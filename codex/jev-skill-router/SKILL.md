# Recommend skills for this Codex session

1. Preserve any other skill the user explicitly requested. If they chose one, continue with the native Codex workflow and skip this router.
2. Prepare a short, shareable task summary and a list of candidates from the skill inventory already visible in this session. Include enabled candidates whose shareable descriptions could help with any part of the task, including broad capabilities that complement specialized ones. Include only entries with an unambiguous original absolute `SKILL.md` path and preserve qualified names such as `plugin:skill`. Exclude this router. Use a brief, shareable capability description for each candidate. If the inventory is unavailable, or the task cannot be summarized without private information, use native selection.
3. Run the bundled `scripts/recommend.mjs` with Node.js in the current project. Use the absolute path derived from this skill's own location. Pass a JSON object on stdin with `task`, `availableSkills` (each entry has `name`, `description` and `path`) and `explicitlySelected` (other skills explicitly requested by the user, normally empty here). When the task has clear independent deliverables, include `needs` with up to eight concise, non-overlapping requirements grounded in the request. Keep constraints in the task summary and omit `needs` if the task is ambiguous or a local trivial route applies. If a reliable context estimate is already available, pass per-candidate `contextTokens`. Serialize data as JSON and pass it as data, without interpolating user text into shell code. Send no file contents, credentials, transcript, internal identifiers, client data or private project details. Paths are used locally to identify recommendations. The external service receives the sanitized task summary and candidate names and descriptions.
4. Use the existing sandbox for the first invocation. If a `network-unavailable` or `network-blocked` fallback includes `nextAction: "request-network-approval-once"` and session policy permits requesting approval, ask through Codex's approval mechanism for one invocation of this launcher with network access to `api.typesafe.ai`. Explain that this may use TypeSafe credits and sends the shareable task summary and candidate metadata. Request no persistent rule or wider permission. With approval, invoke the same command and stdin once with `--after-network-approval`. If approval is refused or unavailable, the retry fails, or any other failure occurs, use native selection for the rest of the turn. Keep the same sandbox and approval settings. The launcher never retries on its own.
5. Treat `advisory` output as recommendations. Verify each recommended name and path against the current session inventory and load a candidate through the normal skill workflow only when it serves the task. Report recommended skills separately from skills whose instructions you actually loaded and used. The launcher only reports recommendations. Check `rejectedCandidates` and any uncovered needs in `coverage.uncovered`. Use native judgment for those gaps. An empty recommendation leaves normal Codex judgment available.
